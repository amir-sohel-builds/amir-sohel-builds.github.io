The 12 questions I ask before an agent goes live

A demo has to work once. Production has to work on a bad Tuesday, for someone who never read the instructions.

Before an agent goes near real users, I ask twelve questions. Each one has a yes or no answer. Any no blocks the launch.

Almost none of them are about the model. The model is the smallest part of an agent in production. The rest is ownership, evidence, undo buttons, and limits, and that is where launches go wrong.

I turned the list into a script, so the answer does not depend on who is in the room. You can try it in your browser or read the code. Here is the list, and why each question is on it.

The launch gate. Ground it is highlighted because it is the layer I care about most.

Own it

A1Is there a named owner?

A person, not a team alias. The owner is who gets the call when the agent is wrong, and who can switch it off. Without one, a wrong agent keeps running until a customer notices.

I also ask for an escalation contact, but that one only warns. Owners go on holiday.

Ground it

A2Are the approved sources listed?

An agent should know where its answers are allowed to come from. Write the sources down. If you cannot list them, you cannot test them, and you cannot say what the agent should have known.

A3Does it refuse when it cannot verify?

If the answer is not in an approved source, the right output is “I don’t know.” A confident wrong answer costs more than no answer, because people act on it. I wrote more about this in why I made my agents say I don’t know.

Prove it

A4Is there an eval suite?

An agent without evals is an opinion. The suite does not need to be big on day one. It needs to exist, and to run before every release.

A5Does the pass rate clear the bar?

Set the bar before you see the number. The checker defaults to 90, and a team can raise it. A pass rate within three points of the bar still passes, with a warning, because the next prompt change will move it.

Undo it

A6Can you roll it back in one step?

You will ship a bad prompt. The only question is how long it stays live. If undoing it takes a ticket and a meeting, you have a slow outage.

A7Are the prompts versioned?

Treat prompts like code. Then rollback is a pointer change, and when behavior shifts you can say exactly what changed.

Contain it

A9Does every write action need a human to approve it?

Reading wrong is cheap. Writing wrong is not. Anything that changes something, like a refund, a ticket, or a message, waits for a person until the agent has earned more trust, with the evals to show it.

A10Does it run with the caller’s permissions?

An agent on a shared admin credential can see and do more than the person using it. Use delegated access, so it acts as the user and can never go further than they could.

A12Is privacy reviewed when it handles personal data?

Before launch, not after. It is the one conditional check. When it applies, it is not optional.

Watch it

A8Is there a monthly cost cap?

A runaway loop shows up as a bill, not a bug report. Set the cap before launch, and decide what happens when it is hit.

A11Are logs and traces on?

If you cannot see what the agent did, you cannot debug it, audit it, or improve it.

What a script cannot decide

The checker does not judge whether the sources are the right ones, whether the evals are any good, or whether the cap is sensible. It checks that each thing exists and clears the bar your team set. People make those calls, and that is on purpose.

Everything else is deterministic. If a script can ask the question, the LLM stays out of it. It gives the same answer twice, it costs nothing to run, and you can test it. The checker has its own evals, like every skill in the repo.
